# job-search-radar-v2

Weekly NYC equity research / buy-side job tracker (entry-level roles and internships). See `tracker.html` for the current list, `postings.json` for the structured data, and `seen_postings.json` for the dedup log used to avoid re-researching already-classified postings.

## Scan policy notes for future runs

- **In scope: full-time entry-level roles AND internships.** Titles include "equity research analyst," "research associate," "investment analyst" (public equities) for full-time, 0-1 years experience required or explicit entry-level/new-grad language — plus "equity research intern," "research intern," "summer analyst," "summer associate," or any internship explicitly tied to equity/investment research. Internships get no experience-requirement filtering and are in scope regardless of class-year targeting (rising junior through MBA) — timing/eligibility is left for the candidate to evaluate. Every posting carries an `"employment_type"` field (`"full-time"` or `"internship"`), and `tracker.html` shows it as a small badge next to the role so the two are visually distinguishable. An internship whose title names a broad, multi-discipline rotational program (e.g. covering fixed income/private credit/equities together, or a generic firm-wide "internship opportunities" talent pool with no specific team) does not qualify — only include internships explicitly, specifically tied to equity/investment research.
- Once a posting's `date_posted`, entry-level/internship classification is determined, that classification is permanent — never re-research an already-classified posting (efficiency requirement, this runs weekly not daily). This permanence applies to classification only — **"still open" status is a separate check that must be re-run on every posting on every run** (see "still open" verification layer below), including postings whose classification was already settled in a prior run.
- **"Still open" verification layer.** A link loading successfully is not the same as the position still being open, so on every run, re-fetch every posting currently in `postings.json` (not just new ones) and check for:
  - **Closed/filled signals:** language like "position has been filled", "job you are trying to apply for has been filled", "this posting is no longer available", "posting closed", a plain 404/not-found response, or a close-date field (e.g. "Anticipated Posting Close Date") that has already passed relative to today. Any of these means the posting is closed — remove it from `postings.json`/`tracker.html` (same handling as the Workday stale-link rule below), but leave it in `seen_postings.json` so it isn't re-added.
  - **Internship application deadlines specifically.** Campus internship postings (summer analyst/associate programs) commonly carry a fixed application deadline stated separately from the posting's own publish date, and recruiting cycles are typically staffed 6-12+ months ahead of the internship's actual start date — so a posting can look otherwise-qualifying (right title, right location, right class year) while its application window or even its program start date has already passed. Check for both before including a new internship candidate, and treat an already-passed deadline or start date as an affirmative closure signal, not just an "unconfirmed" one.
  - **Unverifiable sources — flag, don't trust silently.** Some sources can't be fetched/checked at all in this environment: sites that block automated access (e.g. robots.txt disallow, or a bot-protection 403 — Third Bridge, RBC's own site, and Glassdoor mirrors are known cases here), and job boards that render content client-side via JavaScript so a fetch returns an empty shell (e.g. prosple.com, Greenhouse-embedded listings like williamblair.com/Careers/job-description). For these, do not treat "page loaded/returned 200 without an explicit closed signal" as confirmation that the role is still open. Instead, set `"verification": "unconfirmed"` on the posting (vs. `"confirmed"` when a direct fetch or live-search-API check actually succeeded and showed no closed signal), and surface it in `tracker.html` with a small "⚠ manually verify still open" note next to the link, rendered less confidently than a fully-verified posting.
- **Strict NYC location check.** "New York" appearing in a posting's text is not sufficient — it has previously caused statewide false positives (e.g. a Goldman Sachs posting actually located in Albany, NY got added as NYC). Read the actual location field on the live posting and confirm it names New York City itself (the five boroughs) or an explicit NYC-area designation — not just any city in New York State. Reject/remove postings located in Albany, Buffalo, Rochester, Syracuse, White Plains, or any other non-NYC New York location, even though they'll contain the string "New York."
- **Exception: Workday-hosted postings** (`*.myworkdayjobs.com`). Workday deep-links can go blank/stale once a requisition closes — the URL stays reachable but shows no content, unlike a clean 404. So Workday postings get extra handling both directions:
  - **When adding a new Workday posting:** don't treat a non-empty fetch of the direct job URL as sufficient confirmation. Also cross-check that the job still appears in the company's live Workday search results (search the site/board for the exact title) before adding it to `postings.json`.
  - **On every subsequent run:** re-verify each Workday posting already in `postings.json` against the company's live search results (unlike every other source, these are NOT exempt from re-checking). If a previously-added Workday posting no longer appears in live search results, remove it from `postings.json` and `tracker.html` — but leave its entry in `seen_postings.json` so it isn't mistakenly re-added if it briefly reappears.
- **Environment note:** in the sandboxed execution environment this scan runs in, the Adzuna API and most companies' own career-site domains (direct Greenhouse/Lever API calls, rbc.com, stifel.com, wellington.com, alliancebernstein.com, etc.) are blocked by the outbound network policy (403 on CONNECT). `*.myworkdayjobs.com` Workday CXS endpoints are reliably reachable directly — including the POST `/wday/cxs/<tenant>/<site>/jobs` search endpoint, which is the fastest way to run the mandatory live-search cross-check. For everything else, `WebSearch` (not `WebFetch`/`curl`) is the only working channel — cross-reference multiple search snippets to confirm a posting's real qualifications text before counting it as entry-level, and when the actual text can't be confirmed, exclude the posting rather than guess from the title.
- **Unconfirmed-staleness rule (6-week cap).** Some sources can never be directly confirmed either way (Third Bridge, prosple.com, Glassdoor mirrors, JS-rendered listings like williamblair.com's Greenhouse embed) — see "Unverifiable sources" above. Left unchecked, a posting there could sit in the tracker indefinitely even after the role is actually filled, since there's no way to observe its closure. To bound that: every posting carries a `"first_seen_unconfirmed"` date field, set the first run its `"verification"` is `"unconfirmed"` (equal to `date_found` if it was unconfirmed from the moment it was added). On every run, for every posting currently `"unconfirmed"`, if `first_seen_unconfirmed` is 6+ weeks (42+ days) in the past relative to today, remove it from `postings.json` and `tracker.html` — but keep it in `seen_postings.json` (same handling as every other removal in this policy) so it isn't re-added. If a posting's `verification` ever flips from `"unconfirmed"` to `"confirmed"`, drop the `first_seen_unconfirmed` field (it's no longer accruing staleness). If it flips from `"confirmed"` back to `"unconfirmed"` (e.g. a source that briefly became fetchable stops being reachable again), reset `first_seen_unconfirmed` to that day, not the posting's original `date_found`. This check runs alongside, not instead of, the "still open" verification layer above — a posting can be removed either because an explicit closed signal was found, a Workday live-search check came up empty, or (this rule) it's been unconfirmed for too long with no path to ever finding out.
- **Third-party mirrors can surface stale Workday requisitions.** ZipRecruiter/Lensa/etc. mirrors of `*.myworkdayjobs.com` postings can keep indexing a req long after it's closed. On 2026-08-03 a KeyBanc "Equity Research Associate, FinTech" (R-39632) surfaced only via such mirrors; the direct Workday CXS job endpoint 404'd and it did not appear in a live `jobs` search for "Equity Research" at all (only the 2 already-tracked KeyBanc reqs did). It was excluded from `postings.json` but logged in `seen_postings.json` with a note so it isn't re-researched. Treat mirror-only sightings of Workday jobs as a prompt to run the live CXS search check before adding, not as confirmation on their own.
